# Guidance for coding agents

A downstream Linux tree for the Xiaomi Pad 8 Pro (`piano`, SM8750). For AI agents working here on behalf of a contributor. [.github/CONTRIBUTING.md](.github/CONTRIBUTING.md) is the authority; commits, the DCO and attribution follow the target kernel's `Documentation/process/submitting-patches.rst` and `coding-assistants.rst`.

- **Target and scope.** Target `piano/dev`; fetch it from this project's repository (your `origin` may be a fork), rebase onto it and review the complete final diff. Configuration fragments live here under `arch/arm64/configs/`; userspace, packaging and the list of release fragments (`kernel/source.json`) live in [xiaomipad-8pro-mainline](https://github.com/yzddmr6/xiaomipad-8pro-mainline); open a companion PR there and state the merge order.
- **One topic per PR.** Each commit is one logical change that builds on its own; split bindings, drivers and board enablement.
- **Read before you write.** Follow the real call path and every existing consumer. When you add a device-tree child node, check every driver that walks that parent's children. Fixed reserved-memory addresses must lie inside RAM on every supported memory size. Hardware parameters need a stock or upstream reference valid for both panels.
- **Build as releases are built.** Use every release fragment listed in `kernel/source.json`, in order; check that the options you need are really set in the final `.config` (unmet dependencies are dropped silently); no new warnings; run checkpatch on your series and `dt_binding_check`/`dtbs_check` for changed bindings or DTS. Probe failure, remove and power-state paths must release what they took.
- **Make claims checkable.** Feature and fix statements must match the final diff and the real call path; test statements name the build, scenario and result; after a rebase, say which evidence still applies. Check error paths by source review or offline fault injection, not by unbinding drivers of hardware in use.
- **Device tests are the contributor's.** Ask them to run CONTRIBUTING item 6 and paste sanitised results; never report a test you did not see run. Do not flash, wipe or reboot a device unless the contributor explicitly asks, and only the device they named.
- **Attribution.** Never add `Signed-off-by:` (the human contributor certifies the DCO), `Tested-by:` or `Reviewed-by:` for anyone. Add a trailer naming the model that actually did the work, `Co-Authored-By: <model> <email>` (for example `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`) or the `Assisted-by: <agent>:<model version>` format of the kernel 7.2 `coding-assistants.rst`, one per model; if you do not know your exact model, ask the contributor rather than guess. State the tools and models in the PR; never paste prompts, session logs or private task notes into commits or PRs. Keep the author, date, trailers and `Link:` of imported patches; put local changes in separate commits.
- **Hard limits.** Do not allocate ABI numbers or touch the integration repository's ABI ledger or release locks. Do not print serial numbers, device addresses or calibration at default log levels, and keep personal data out of commits.
